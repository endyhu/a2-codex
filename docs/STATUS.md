- **What it is:** a tool, not a cheatsheet. Inputs: class, PvE/PvP focus, which standard boards (Nezekan, Zikel, Vaizel, Triniel) and the crystal pool for each of the three pools (a pool of 0 skips Ariel/Azphel), an ordered "Must-have skills" list, and right-click on a skill chip ignores or un-ignores it (long-press on touch; ignored skills score nothing, so they never pull the route; saved per class in `ignored`). Output: the provably best connected route per board, recomputed live (120ms debounce, no Optimize button); about 0.05 to 0.4s. Status text shows "Optimal · time". Settings persist in `localStorage` (`a2codex-daevanion-v1`).
- **Algorithm:** `src/scripts/daevanion-solver.ts`, ported unchanged from the standalone optimizer (frontier DP per board, knapsack across boards sharing a pool, lexicographic tier scoring, `verify()` on every result). Checked against the old page: identical stat totals for Gladiator PvE 400, Cleric PvP with all six boards, Ranger PvE with all six boards. `weigh()` builds the tiers: must-have actives (in order) > orange rewards > must-have passives > Attack Bonus > Critical Hit > other passives > other actives > other stats (PvE: one soft-weighted tier; PvP: one strict tier each). Old tool's three skill lists (key actives, key passives, extra actives) became one list that is split by skill type, so key passives still follow orange rewards. Cross-checked with the Aion 2 Bible's Daevanion chapter (key actives, then orange, Attack Bonus tiles valuable, Multi-hit Resist and Critical Damage Tolerance oranges worthless in PvE, Ariel orange = PvE Damage Boost/Tolerance): all match. The Bible also lists Marchutan and Yustiel individual boards that are not in our data (unknown if on Global); it calls Azphel PvP, skip. Azphel and Ariel keep their fixed orders (orange first). Stat orders are fixed, no editing UI (owner chose skills only + mode).

## Market (`src/pages/market/index.astro`), finished
- **What it is:** a tool. Filters (region, faction, Servers: Launch (default) / Early Access / Both, item type, saved in `localStorage` `a2codex-market-v1`) and a searchable table of items listed on at least one of the chosen servers (one-server items show "only one server"; items with no listing there show their last known price dimmed): cheapest server and price, most expensive server and price, gap in % and Kinah. A Server dropdown (servers of the chosen region and faction; not saved) switches the table to one server: its price and rank, the cheapest server, and how much more it costs than the cheapest, with that server marked in the breakdown. Sortable headers; click a row for every server's price, listings and % above the cheapest. Compares within one region at a time (default Europe); Elyos and Asmodian servers can be compared together or separately. The table scrolls inside the panel (sticky header, filters panel sticky beside it); rows are drawn 120 at a time and the next 120 are added when the list is scrolled near its end (a filter click takes about 15 ms instead of 300 ms with 1000 rows). Filters, the Server and the search are in the address bar (`?r=EU&f=Asmodian&l=all&sec=weapons&srv=12318&q=...`, `src/scripts/urlstate.ts`; the URL wins over the saved settings on load). Default order is "Most traded": Kinah traded per item in the API's 28-day sales window (Wrathful/Radiant materials, Refining and Amplify Stones on top); the number comes from EU Kaisinel only, because the API has sales stats for its default server alone (other servers return null), and is stored per item in `items[i][4]`.
- **Data:** `scripts/market-snapshot.mjs` (`mise exec -- node scripts/market-snapshot.mjs`, all 106 servers (`wanted` in the script can narrow it for a test run), otherwise 106 requests, 4 at a time, retries with exponential backoff, one extra pass over skipped servers, gives up after 8 servers fail: about 1 minute when the API is healthy, but 503 spells made a test run take 10 minutes and answer only 87 of 106 servers (old file kept); the workflow step has a 15 minute timeout) writes `public/market.json` (about 1.4 MB with last prices, loaded client-side by Market and Crafting). It is committed as a fallback (last full run: 106 servers, 1332 items). `deploy.yml` deploys the site first (reusing the live market.json), then a second job fetches a fresh snapshot, rebuilds and deploys again if the fetch worked (skipped when the live market.json is under 1 hour old); `.github/workflows/market-refresh.yml` does a fresh build and deploy every 6 hours. Neither commits anything. Source and rules: `docs/data-sources.md` > Market page.
- **Last price:** the snapshot also stores `last[itemKey] = [serverId, price, hours since epoch, ...]` for items with no listing right now (from `last_price` / `last_seen_at`, seen within 60 days, only items listed somewhere; the full run gave 1290 items). Market: with a Server chosen, items not listed there appear with their last price dimmed and its age ("last price · 4 d ago"). Crafting: a missing price falls back to the last price (dimmed, "last price · N d ago"; the totals count them). **Price history chart removed (owner):** the API's `/api/items/{key}/prices` takes `bucket=1d` and works, but it sends no CORS header (browsers block it) and takes about 2 s. It needs a small proxy (Cloudflare Worker with caching) or history baked into the snapshot; neither is built.
- **Default region:** first visit picks the region from the browser's time zone (`src/scripts/region.ts`: Europe, Africa, Atlantic -> EU; US east/west, Latin America, Asia/Australia/Pacific map to NAE, NAW, LA, AS; falls back to EU or the first region in the data). Nothing is sent anywhere. Used by Market and Crafting.
- **Not done / open:** defaults (all servers, all items, 6 h refresh) were chosen without asking the owner. Outlier single listings make the Gap sort noisy (the minimum-listings filter was removed by the owner, so every listing counts). No price history (see above), no per-item deep link. The two-step deploy and the 6-hour schedule are untested on GitHub until the first push. Phone layout checked by DOM measurements only (no overflow at 360), not by eye; the preview pane was too small to judge 1920/3440 visually (widths measured: main 1500px, no overflow).

## Crafting (`src/pages/crafting/index.astro`), finished
- **What it is:** a tool. Pick a profession, an item type (Daggers, Greatswords, Top, Rings, Components ...) and a recipe from the list of all 512 Global recipes, plus an amount. The table lists the ingredients with the cost on your server, at the cheapest server and at the most expensive server. Filters like Market (region, faction, Servers launch / Early Access; no listings filter, every listing counts) plus "Your server" (None hides that column). Region defaults from the time zone. Settings and the chosen recipe persist in `localStorage` `a2codex-crafting-v1` and in the address bar (`?r=EU&f=Asmodian&l=all&srv=12318&p=Blacksmithing&t=Greatswords&k=110130019.0&n=2&h=610650012:1`, where mastery is only saved locally (not in the link) and `h` is the "have" counts as item path:count for the open recipe, not saved locally; the URL wins on load).
- **List:** sorted by item level (metabot item lists; plain Common gear has none, so mastery is used), then mastery, then name. Recipes only the other faction can craft are hidden: faction is your server's, else the Faction filter, else all show. When the faction changes, the open recipe switches to its twin (same name, or the recipe of the same tier, e.g. Star Dragon Lord <-> True Dragon Lord) or closes. 40 products have two recipes with the same product id: those are the two factions' variants (different herbs, wood), so components use the one of your faction and the list only says "Recipe 1 of 2" when both show.
- **Table as a tree:** the recipe's own ingredients in recipe order. A craftable component has a Craft / Buy switch with both costs (default: the cheaper one in your server's prices, the cheapest column with no server; resets when another recipe is picked). Craft opens it into indented rows. Levels: tinted rows and a 3px bar in one colour per level (violet, teal, amber, pink), rows of one level join into one solid bar, ancestor levels continue as faint dotted bars, the row line runs the full cell width under the bars, small "Ingredients for <parent>" label on the first child; 26px per level (11px on phones). A crafted component's price cells show its subtotal, dimmed; only leaf rows add to the Total. `.nest` is the tree-row class (do not call it `.sub`, that is the item-type row).
- **Have / total:** every row has a stepper (the box is a text input with numeric keypad, because number inputs lose the caret on the re-render per keystroke; the caret is restored at the end) for how many you already have (starts at 0, capped at the total, keyed by the row's path so the same item in two branches counts separately); prices cover the rest. The mouse wheel over a have box or the Amount box adds or removes one once that box has focus (so scrolling the page over the table still works).
- **Combos:** an item that is the Splendent combo result of a recipe (the item both factions share a name for, e.g. Artisan's Splendent Orichalcum Greatsword) is a component too. Craft = one craft of the base recipe per item (no compounding across tiers; the rows below are one craft, dimmed, not added again) but its price cells and the Total use the expected cost: one craft / (success x combo activation x combo success at your mastery). The row says "N% combo · ~M crafts · Z first try", the Total says combo items count at expected cost. The Splendent name rule is inferred (Splendent + name, or Artisan's / Expert's Splendent ...; guides agree and 114 recipes use the derived item as an ingredient); Food has none. Matching is by name because the factions have different ids for one name.
- **Summary cards:** Sells for (product price x items made; your server, else the best server), Profit (needs a server with every material priced; no market fee assumed), If it combos (price of the Splendent item), Cheapest single server last (cheapest total of the first-try shopping list on one server, preferring servers that list every material, with a "not listed there" count). A Mastery box (empty = the recipe's mastery) sets success and combo chances; below the recipe's mastery it says it is locked. Mastery is per profession (Blacksmithing, Armorsmithing, Handicrafting, Alchemy, Cooking): the box is labelled and filled for the open recipe's profession, and a component crafted from another profession's recipe uses that profession's mastery. Saved locally as `mast: {profession: level}` (an old single number is dropped).
- **Dragon Lord Splendent recipes:** the client table lists only the extra materials for the 114 "Splendent X" recipes (mastery 0, item level 70/86/102), but X itself is consumed too (owner, in game), so `crafting-snapshot.mjs` adds one X (the same name without "Splendent", faction and type) as an ingredient. X is then a normal component (craft or buy, with its own combo chance). Quantity 1 is assumed. Artisan's and Expert's Splendent items have no recipe (combo only).
- **Prices:** Market snapshot (`public/market.json`) by item id (the product's Sells for also looks up other ids with the same name: 38 of 512 recipe products are listed on the market under a different id, e.g. Splendent Star Dragon Lord Greatsword 110130100 vs 110130021; no ingredient is affected). No listing -> the last known price (dimmed, with its age). "(Bound)" materials are sold by NPC merchants: Kina price from the shop pages (`vendor` in crafting.json), which caps every column. Materials with neither show "—" and "N without a price" in the Total.
- **Data:** `public/crafting.json` from `scripts/crafting-snapshot.mjs` (metabot.gg: recipes, item levels from the weapon/armor/accessory lists, factions from the item pages, success/combo curves, shop prices; about 2 minutes, re-run after patches). Details and source rules: `docs/data-sources.md` > Crafting page.
- **Not done / open:** multi-recipe list (owner will decide later); plain recipes are shown at 100% success (the success chance is shown above the table, but not used in plain-craft costs); guides say a failed craft consumes its materials (the combo expected cost relies on it) but that is from secondary sites, not NCsoft; faction of same-name pairs is verified against the market only where the items have listings (190 of 512 recipes have such evidence, 0 wrong); the combo item name rule is inferred; the tree visuals were checked at 360, 1920 and 3440 in an emulated viewport, not on a real phone.

## Page switches (Astro `ClientRouter` in `Base.astro`)
- Full page loads showed a blank frame in Vivaldi/Chromium on every click, so the site uses Astro's client-side router: it fetches the next page and swaps it in, no reload. The sidebar (phone: top bar) has its own `view-transition-name` and stays still; the content crossfades in 0.12s and the browser's own 250ms page-group animation is off (off entirely for reduced motion); a switch takes about 160ms on the built site. The dev server renders Stats and Gear on each request (about 300ms), so judge speed with the `astro-preview` launch config (built site, port 4322) after `npm run build`. `scrollbar-gutter: stable` keeps the layout from shifting sideways between short and long pages.
- **Page scripts** run inside `document.addEventListener('astro:page-load', ...)`, return early when their page's element is missing, and pass `{ signal }` to every window/document listener (aborted on `astro:before-swap`). New pages with scripts must follow the same pattern. Base's own script runs once and uses delegated clicks.
- **Theme:** the incoming page's `<html>` says dark, so `astro:after-swap` re-applies the saved theme; the `color-scheme` meta follows the theme.
- **Section links on the current page** get `data-astro-reload` on each page load so the browser does the smooth scroll (the router would jump instantly); a `hashchange` handler copies router state onto that history entry so Back still swaps pages correctly.
- **Testing:** the router waits for a painted frame, so it stalls while the preview pane is hidden (call `show_pane` first). Use real clicks (`computer`) to judge transitions. `Transition was skipped` console errors only came from hidden-pane or scripted tests.
- **Update banner:** `astro.config.mjs` bakes a build id into the pages (`__BUILD_ID__`) and writes `dist/version.json`. Base checks it on tab focus and every 5 minutes (`no-store`); when it differs, the persisted `#update` bar (green, top middle; "New version available" with a round refresh-icon button that spins on hover) appears. Not shown in dev (no version file). Not yet checked: that the bar stays visible across a router page switch (the hidden preview pane stalls switches; use a real click with the pane shown). Clicking the arrows sets `sessionStorage.updating`; from then on each page's first router load is preceded by a `cache: 'reload'` fetch (`astro:before-preparation`), because GitHub Pages' ~10 min cache served old-build pages whose old script re-showed the bar. Fix is from code reading; not reproduced on a live deploy.
- **Data files after an update:** Market and Crafting fetch `market.json` / `crafting.json` with `cache: 'no-cache'` (revalidate), otherwise Pages' ~10 min HTTP cache served old prices after the banner's reload. New data fetches must do the same.

## How to test the layout (the browser pane is narrow)
- Desktop and ultrawide: load the page in an iframe sized 1280, 1920 or 3440 wide and scale it down with CSS transform, then measure with JS. Check phone width at about 360.
- Call `show_pane` (preview) before taking screenshots, or they time out.
- Animations barely run in the hidden preview pane. To judge a glow, add the `flash` class by script and freeze it with a style override (`animation: none; opacity: 1` for the step strips), then compare frozen frames; check sizes and edges with `getComputedStyle(el, '::after')`.
- The dev server can serve stale CSS or layout code after many edits: restart it (`preview_stop`, `preview_start`) or hard refresh before judging a change.
